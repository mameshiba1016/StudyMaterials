# 01 UE C++の全体像と標準C++との違い

## 1. 最初に持つべき全体像

UEで書くC++も、最終的にはC++コンパイラが機械語へ変換します。しかし、その前後にUE独自の道具と規約が入ります。

```text
人間が書いた .h / .cpp
        ↓
UHTがヘッダを解析し、リフレクション用コードを生成
        ↓
UBTがモジュール依存関係・設定・生成物をまとめる
        ↓
C++コンパイラが各翻訳単位をコンパイル
        ↓
リンカがモジュールや実行ファイルを構築
        ↓
UEエディタまたはゲームがロードして実行
```

- **C++コンパイラ**：C++の文法、型、テンプレートなどを処理します。
- **UHT（Unreal Header Tool）**：UEが認識すべき型・関数・プロパティのメタデータと補助コードを生成します。
- **UBT（Unreal Build Tool）**：どのモジュールを、どの設定と依存関係でビルドするかを管理します。
- **UEエディタ**：生成されたメタデータを使い、Details、Blueprint、保存、複製などを実現します。

したがって、UEのエラーには「C++文法エラー」「UHT解析エラー」「モジュール依存エラー」「リンクエラー」「実行時エラー」があります。表示された最初のエラーと、どの段階で止まったかを読む習慣が重要です。

## 2. 標準C++とUE固有機能を分類する

```cpp
#include "CoreMinimal.h"       // UEのヘッダを取り込むプリプロセッサ命令。
#include "GameFramework/Actor.h" // AActorの宣言があるUEヘッダ。
#include "SampleActor.generated.h" // UHTが生成するヘッダ。原則として自作ヘッダ内の最後のinclude。

UCLASS()                        // UE固有：次のクラスをリフレクション対象として宣言する。
class MYGAME_API ASampleActor : public AActor // C++のクラス宣言。MYGAME_APIはDLL境界の公開指定。
{
    GENERATED_BODY()            // UE固有：UHTが生成した宣言をクラスへ差し込む。

public:                         // ここから標準C++のアクセス指定。
    ASampleActor();             // 標準C++のコンストラクタ宣言。

    UPROPERTY(EditAnywhere)     // UE固有：エディタ編集可能というメタデータを付ける。
    float MoveSpeed = 600.0f;   // 標準C++のデータメンバ宣言と初期化。

    UFUNCTION(BlueprintCallable) // UE固有：Blueprintから呼べるというメタデータ。
    void StartAttack();          // 標準C++のメンバ関数宣言。
};
```

マクロを全部「特殊なC++」と曖昧に覚えないでください。`class`、継承、アクセス指定、コンストラクタ、メンバ関数は標準C++です。`UCLASS`などはプリプロセッサとUHTが扱うUEの注釈です。

## 3. エンジンが呼ぶコードと、自分が呼ぶコード

ゲームフレームワークでは、エンジンが決められたタイミングでこちらの関数を呼びます。これはコールバックまたは制御の反転と呼ばれます。

```cpp
void ASampleActor::BeginPlay()
{
    Super::BeginPlay(); // 親クラスが必要とする開始処理を先に実行する。
    // レベル上でゲームが始まった後の初期化を書く。
}

void ASampleActor::Tick(float DeltaSeconds)
{
    Super::Tick(DeltaSeconds); // 親のTick契約を保つ。不要なTick自体は無効化すべき。
    // DeltaSecondsは前フレームからの経過秒。速度×時間でフレーム依存を避ける。
}
```

`BeginPlay()`を自分で適当に呼ぶのではなく、エンジンがライフサイクルに沿って呼びます。一方、`StartAttack()`のようなゲーム固有関数は、入力、AI、Abilityなどから自分の設計に従って呼びます。この違いを理解すると、初期化順序のバグを減らせます。

## 4. C++とBlueprintの役割

- C++：土台となる型、複雑なロジック、再利用可能なシステム、性能が重要な処理、チームで保守する契約。
- Blueprint：アセット参照、演出の調整、レベル固有処理、デザイナーが頻繁に変更する値や流れ。
- Data Asset／Data Table：キャラクター性能、攻撃定義、敵設定などのデータ。

高速アクションでは、攻撃を巨大な1個のBlueprintへ直書きするより、C++側に「攻撃定義を実行する仕組み」を作り、アニメーション・威力・硬直・キャンセル窓・VFXなどをデータ化する方が拡張しやすくなります。

## 5. よくある誤解

1. **UEならメモリを考えなくてよい**：誤りです。GC対象外のC++資源、循環参照、非同期処理、無効なActor参照などは設計が必要です。
2. **すべてTickで処理すればよい**：誤りです。イベント、Timer、Animation Notify、Delegateを使い、必要な時だけ処理する方が明確で軽量です。
3. **Blueprintは遅いから全部C++**：極端です。処理頻度、保守性、調整担当を見て境界を決めます。
4. **エディタで見える参照は必ず安全**：誤りです。破棄、レベル遷移、非同期ロード、GCを越えて有効か確認が必要です。

## 6. 学習時の読み方

UEのコードを見たら、次の順で読みます。

1. この型は`UObject`、`Actor`、`Component`、普通のC++型のどれか。
2. 誰が生成し、誰が所有し、いつ破棄するか。
3. エンジンが呼ぶ関数か、ゲーム側が呼ぶ関数か。
4. `UPROPERTY`等でエンジンに認識される参照か。
5. 毎フレームか、イベント時だけか。
6. C++のロジックか、編集用データか、演出か。

この6点が分かれば、長いクラスでも構造を見失いにくくなります。
