# 2Dゲームの全体構造

2Dゲームも、入力を受け、状態を更新し、結果を描画・再生するリアルタイムソフトウェアです。画像を動かすだけでなく、寿命、順序、時間、リソース、シーンを設計します。

## 一フレームの基本的な流れ

```text
OSイベント取得
    ↓
入力状態を一フレーム分へ確定
    ↓
ゲーム状態を更新
    ↓
衝突検出・解決
    ↓
破棄・生成要求を安全な地点で反映
    ↓
描画コマンドを生成
    ↓
画面へ提示
```

実際には物理の固定更新、UI、オーディオ、非同期ロードなどが加わります。重要なのは、同じフレーム内の処理順がゲーム仕様になることです。

## 最小の責任分割

```cpp
class Game
{
public:
    bool Initialize();
    void ProcessEvents();
    void Update(double deltaSeconds);
    void Render();
    void Shutdown();

    [[nodiscard]] bool IsRunning() const;

private:
    bool isRunning_{true};
};
```

- `Initialize`：ウィンドウ、描画、入力、初期シーン等を構築。
- `ProcessEvents`：終了、リサイズ、デバイス接続等を取得。
- `Update`：ゲーム世界の状態を変化。
- `Render`：現在状態から描画結果を作る。
- `Shutdown`：依存関係と逆順に終了。

描画中にゲームルールを変更する設計は、描画回数やカリングで挙動が変わるため避けます。

## サブシステム例

- Platform：ウィンドウ、OSイベント、ファイルパス。
- Renderer：テクスチャ、描画コマンド、画面提示。
- Input：キーボード、マウス、ゲームパッドをアクションへ変換。
- Audio：SE、BGM、ボイス。
- Asset：画像、音、フォント、データのロードと寿命。
- Scene：タイトル、ゲーム、リザルトなど大きな状態。
- World：Entity、衝突、ルール、生成・破棄。
- UI：HUD、メニュー、フォーカス、解像度対応。
- Debug：ログ、可視化、プロファイラ、チートコマンド。

最初から巨大なManager群を作るのではなく、必要になった責任を明確な所有者へ置きます。

## 初期化順と破棄順

描画リソースは描画デバイスへ依存します。テクスチャを保持したまま先にRendererを破棄すると、テクスチャのデストラクタが無効なデバイスへアクセスする可能性があります。RAIIとメンバー宣言順を使い、依存先が利用者より長生きするようにします。

```text
作成：Window → Renderer → Assets → Scene
破棄：Scene → Assets → Renderer → Window
```

## 更新中の生成・破棄

`vector`内の敵を走査中に直接追加・削除すると、イテレータ無効化や更新順の不公平が起きます。

```cpp
void World::Update(double deltaSeconds)
{
    for (Entity& entity : entities_)
    {
        entity.Update(deltaSeconds, commandBuffer_);
    }

    // 全Entityの走査後、安全な同期点で要求を反映する。
    ApplyDestroyRequests();
    ApplySpawnRequests();
}
```

Command Bufferや削除フラグを用い、「同じフレームに生成された弾はいつから更新されるか」を仕様化します。

## Entityの表現

小規模作品なら値型の構造体と`vector`で十分です。

```cpp
struct Bullet
{
    Vector2 position{};
    Vector2 velocity{};
    float remainingLifetimeSeconds{};
    bool isActive{true};
};
```

規模が増えたら、継承、コンポーネント、ECS、オブジェクトプールを比較します。パターン名から選ばず、要素数、更新方法、組合せ、ツール要件を測ります。

## ゲーム状態と表示状態

ゲーム状態はHP、位置、敵状態などルール上の真実です。表示状態は補間位置、画面揺れ、残像、UIアニメーションなど見た目のための状態です。両者を分けると、ヒットストップ中もUIだけ動かす、固定更新間を滑らかに描画する、といった制御が可能です。

## データ駆動

攻撃力や速度をコードへ散らさず、検証された設定データとして読み込みます。ただし、データ駆動は「何でも文字列で指定」ではありません。型、単位、必須項目、範囲、バージョンを定義し、不正データをロード時に失敗させます。

## 完成に必要な非表示機能

完成したゲームでは、プレイ画面以外も品質になります。

- 起動失敗時のエラー。
- 解像度・音量・キー設定。
- シーン遷移とロード。
- セーブ破損対策。
- デバッグオーバーレイ。
- クラッシュ調査用ログ。
- フレーム時間計測。
- アセット権利表示。
