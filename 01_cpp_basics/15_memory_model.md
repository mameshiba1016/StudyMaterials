# メモリ、オブジェクト、スタック、ヒープ

## C++におけるオブジェクト

C++のオブジェクトは、型、記憶領域、寿命を持つ実体です。クラスのインスタンスだけをオブジェクトと呼ぶわけではなく、`int`や配列もオブジェクトです。

## プロセスの典型的な領域

実際の配置はOS、ABI、ビルド設定、最適化に依存しますが、学習上は次のように整理できます。

- コード領域：実行命令。
- 静的領域：静的記憶域期間を持つデータ。
- スタック：関数呼び出し情報や自動変数に使われることが多い。
- ヒープ：動的確保に使われる領域。

これはC++規格が物理配置をそのまま保証する図ではありません。ローカル変数がレジスタ化・除去されるなど、最適化後の実体は単純な図と異なります。

## スタックフレーム

関数呼び出し時、戻り先、保存レジスタ、引数、ローカル値などのためにスタックフレームが使われることがあります。関数から戻るとまとめて巻き戻せるため高速ですが、容量は有限です。

```cpp
void DangerousRecursion()
{
    int localData[1024]{};
    DangerousRecursion(); // 終了条件がなく、フレームを積み続ける。
}
```

深い再帰や巨大なローカル配列はスタックオーバーフローの原因になります。

## 動的記憶域

実行時に必要量が決まる長寿命データは動的記憶域を使う場合があります。

```cpp
int* value{new int{42}}; // intを動的確保し、そのアドレスを受け取る。
delete value;             // 対応するdeleteで破棄・解放。
value = nullptr;          // 解放後のポインタを再利用しない目印。ただし別名ポインタは無効なまま。
```

この手動管理は、例外や早期returnで`delete`を通らない、二重解放、配列用`new[]`と`delete[]`の不一致などを起こしやすいため、通常は標準コンテナやRAII型を使います。

## メモリリーク

確保した領域を解放せず、そのアドレスも失うと再利用できません。ゲームではステージ遷移ごとに少量漏れるだけでも長時間プレイで蓄積します。ただし「使用メモリが増えた」だけでリークとは限らず、キャッシュ、アロケータ、遅延解放もあるためツールで追跡します。

## アラインメントとパディング

型には効率的・合法にアクセスするためのアラインメント要件があります。構造体ではメンバー間や末尾にパディングが挿入される場合があります。

```cpp
struct Example
{
    char flag;
    int value;
};
```

`sizeof(Example)`は単純な`1 + 4`とは限りません。大量要素のレイアウトでは影響しますが、可読性を壊して並べ替える前に計測します。シリアライズやネットワークへ構造体の生バイトをそのまま保存すると、パディング、エンディアン、ABI、バージョン差の問題が起きます。

## CPUキャッシュ

CPUはメインメモリより小さく高速なキャッシュを階層的に使います。アクセスした周辺をキャッシュライン単位で読み込むため、連続した配列を順番に処理するコードは局所性を得やすいです。ランダムなポインタ追跡、大きすぎるオブジェクト、頻繁な動的確保は性能へ影響し得ます。

## 仮想メモリ

プロセスが見るアドレスは通常仮想アドレスで、OSとMMUが物理メモリなどへ対応付けます。同じ数値の仮想アドレスが別プロセスで使われても、同じ物理領域とは限りません。ページフォールト、コミット、常駐量などは「確保したバイト数」だけでは説明できません。

## 未定義動作とメモリ

境界外アクセス、寿命終了後の使用、二重解放、不正アラインメント、データ競合などは未定義動作になり得ます。未定義動作は必ずクラッシュするのではなく、最適化によって不可解な結果になる可能性があります。警告、AddressSanitizer、UndefinedBehaviorSanitizer、デバッガ、静的解析を利用します。
