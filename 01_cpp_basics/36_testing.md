# テスト・検証・再現性

テストはバグがないことを証明する魔法ではなく、指定した条件で期待する性質が保たれることを繰り返し確認する仕組みです。

## テストの層

- 単体テスト：小さな関数・型を隔離して検証。
- 統合テスト：複数システム間の接続を検証。
- 機能テスト：プレイヤー視点の一連動作を検証。
- 回帰テスト：過去の不具合が再発しないことを検証。
- 性能テスト：時間、メモリ、ロード量などの予算を検証。
- スモークテスト：起動、ロード、終了など最低限の健全性。

## Arrange・Act・Assert

```cpp
void TestDamageDoesNotGoBelowZero()
{
    // Arrange：前提データを用意。
    Health health{50};

    // Act：検証対象を一度実行。
    health.ApplyDamage(80);

    // Assert：観測結果を期待値と比較。
    assert(health.GetCurrent() == 0);
}
```

実プロジェクトではCatch2、GoogleTest、doctest、エンジンのテスト機能などを使い、失敗箇所、期待値、実値、テスト列挙を得ます。

## 境界値

HP上限100なら、典型値50だけでなく次を検証します。

- 0、1、99、100、101。
- 負数。
- 型の最小・最大付近。
- 空配列、一要素、大量要素。
- null、空文字、壊れたデータ。
- 同じ操作の連続実行。

バグは境界と状態遷移に集中しやすいです。

## 浮動小数点テスト

計算値を完全一致だけで比較せず、目的に合う許容誤差を使います。

```cpp
bool NearlyEqual(float a, float b, float epsilon)
{
    return std::abs(a - b) <= epsilon;
}
```

値の規模が大きく変わる場合は相対誤差も必要です。どの誤差が許されるかはゲーム仕様・数値手法から決めます。

## 依存性注入

時刻、乱数、ファイル、ネットワーク、グローバルシングルトンへ直接依存するとテストが不安定になります。インターフェース、関数引数、テスト用実装を通じて制御可能にします。

```cpp
class IRandom
{
public:
    virtual ~IRandom() = default;
    virtual int Next(int minimum, int maximum) = 0;
};
```

必ずしも全依存を仮想クラス化する必要はなく、テンプレート、関数オブジェクト、値を事前生成する方法もあります。

## プロパティベーステスト

個別の期待値だけでなく「どんな入力でもHPは0以上」「正規化後の非ゼロベクトル長はほぼ1」など性質を、多数の生成入力で検証します。失敗入力を小さく縮小するフレームワークもあります。

## Fuzzing

大量の変形入力をパーサーやネットワーク処理へ与え、クラッシュ、ハング、Sanitizer違反を探します。セーブ・アセット・通信など境界面に有効です。

## Golden test

描画画像、シリアライズ結果、AIログなどを既知の基準と比較します。意図した変更でも差分が出るため、人間の承認フロー、許容差、プラットフォーム差を管理します。

## テストしやすいゲーム設計

- Updateへ時刻を引数で渡す。
- 描画とゲームルールを分離する。
- 乱数seedを固定可能にする。
- 入力を記録・再生できるようにする。
- 状態をシリアライズまたは検査可能にする。
- 一フレーム進めるテストハーネスを作る。

## CI

commitやPull Requestごとにクリーンビルド、テスト、静的解析を実行します。不安定テストを放置して再実行で通す文化にせず、時刻・乱数・非同期・共有環境の原因を修正します。
