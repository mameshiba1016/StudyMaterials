# デバッグ・診断・ログ

デバッグは「勘でコードを変更する作業」ではなく、期待、観測、再現、仮説、検証を繰り返して原因を特定する作業です。

## 再現条件を固定する

1. 期待した結果と実際の結果を分けて記録する。
2. 最小の再現手順を作る。
3. ビルド構成、コミット、OS、GPU、入力データ、乱数seedを記録する。
4. 毎回起きるか、頻度、最初に壊れるフレームを確認する。
5. 症状が出た場所と原因が発生した場所を区別する。

クラッシュ行だけを直しても、以前の境界外書込でメモリが壊れた結果かもしれません。

## ブレークポイント

指定位置で実行を停止し、変数、コールスタック、スレッド、メモリを確認します。

- 通常ブレークポイント：行・関数で停止。
- 条件付き：`enemyId == 42`など成立時だけ停止。
- ヒットカウント：指定回数目で停止。
- データブレークポイント：特定メモリが書き換えられた時に停止（対応条件あり）。

最適化ビルドでは変数の除去・並べ替えで、ソース行と命令対応が直感どおりでない場合があります。

## ステップ実行

- Step Into：関数内部へ入る。
- Step Over：呼び出しを一まとまりとして次へ。
- Step Out：現在関数の終了まで進む。

外部ライブラリへ入り込みすぎず、コールスタックから自作コードと引数を追います。

## コールスタック

現在位置へ至った関数呼出列です。nullアクセスが`Enemy::Update`で起きたなら、誰が破棄済みEnemyを更新一覧へ残したか上位フレームとデータ履歴を追います。スタックが破損している場合、バッファオーバーラン等も疑います。

## ログ

```cpp
void LogDamage(EntityId attacker, EntityId target, int amount)
{
    std::clog << "damage attacker=" << attacker.value
              << " target=" << target.value
              << " amount=" << amount << '\n';
}
```

有用なログは、時刻、フレーム、スレッド、カテゴリ、重要ID、状態遷移、エラー文脈を構造的に残します。毎フレーム大量出力はI/Oとロックで挙動を変え、容量を圧迫します。レベル、カテゴリ、レート制限、リングバッファを設計します。

## `assert`・`static_assert`

```cpp
assert(index < enemies.size());
static_assert(sizeof(std::uint32_t) == 4);
```

`assert`は実行時の開発契約、`static_assert`はコンパイル時条件です。外部入力の検証をリリースで消える`assert`だけに任せません。

## Sanitizerと静的解析

- AddressSanitizer：境界外、use-after-free等。
- UndefinedBehaviorSanitizer：一部の未定義動作。
- ThreadSanitizer：データ競合。
- clang-tidy、MSVC Code Analysis等：危険なパターンを実行前に検出。

一つのツールがすべて検出するわけではありません。警告、テスト、レビュー、実機検証と組み合わせます。

## クラッシュダンプ

リリース環境ではデバッガを直接接続できないため、例外コード、スレッド、レジスタ、メモリ、モジュール情報をダンプへ保存します。正確なビルドの実行ファイルとシンボル（PDB等）を保管し、アドレスを関数・行へシンボル化します。

## 二分探索

問題を起こす入力範囲、コミット、システム、フレーム区間を半分ずつ切り分けます。`git bisect`は良いコミットと悪いコミットの間から原因候補を効率的に探せます。テストを自動化できればさらに強力です。

## デバッグ表示

ゲームでは当たり判定、速度ベクトル、AI経路、状態名、座標軸、フレーム時間を画面へ可視化します。内部状態を見えるようにする機能は、完成後のおまけではなく開発速度を支える製品機能です。
