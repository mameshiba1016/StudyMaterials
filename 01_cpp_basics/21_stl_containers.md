# STLコンテナの選択

標準ライブラリのコンテナは、要素の所有、配置、検索、追加・削除を管理します。「何となく`vector`」でも「検索だから常に`unordered_map`」でもなく、アクセスパターンと無効化規則から選びます。

## `std::vector`

可変長の連続配列です。

- ランダムアクセス：定数時間。
- 末尾追加：償却定数時間。
- 中央の挿入・削除：後続要素の移動が必要。
- 連続配置：キャッシュ、C API連携、GPU転送に有利。
- 再確保：ポインタ・参照・イテレータを無効化。

ゲーム内の更新対象、頂点、コマンド、密なデータの基本候補です。

## `std::array`

コンパイル時固定長の連続配列です。要素数も型の一部で、スタック上のローカルや他オブジェクトのメンバーとして直接含まれることが一般的です。固定数の入力ボタン状態、行列要素、小さなテーブルなどに向きます。

## `std::deque`

両端への追加・削除を効率的に行うコンテナです。通常、全要素が一つの連続領域ではありません。`vector`と異なる無効化規則があり、ポインタの安定性を思い込みで判断せず仕様を確認します。

## `std::list`

双方向連結リストです。位置が分かっていれば要素自体を動かさず挿入・削除できますが、各ノードの個別確保、ポインタ追跡、キャッシュミス、メモリ増加が問題になりやすいです。中央削除があるという理由だけで選ばず、`vector`での実測と比較します。

## `std::map`

キー順に整列された連想コンテナで、一般的に平衡二分探索木です。

- 検索・挿入・削除：対数時間。
- キー順の走査が可能。
- ノードベースで要素ごとの確保コストがある。

## `std::unordered_map`

ハッシュテーブルによる連想コンテナです。

- 平均的検索：定数時間。
- 最悪計算量は線形になり得る。
- 順序は意味ある並びとして使えない。
- リハッシュでイテレータが無効化される。
- ハッシュ、等値比較、負荷率、メモリ局所性が性能へ影響。

```cpp
std::unordered_map<std::string, int> itemCounts{};
itemCounts.emplace("Potion", 3);

auto found{itemCounts.find("Potion")};
if (found != itemCounts.end())
{
    std::cout << found->second;
}
```

存在確認だけなのに`operator[]`を使うと、キーがない場合に既定値を挿入します。検索は`find`、C++20なら`contains`を使い分けます。

## `std::set`・`std::unordered_set`

値そのものをキーとして重複なしで保持します。順序が必要なら`set`、平均的な高速検索が中心なら`unordered_set`を候補にします。小さな要素数では、ソート済み`vector`の方が局所性により速い場合もあります。

## コンテナアダプタ

- `std::stack`：LIFO。
- `std::queue`：FIFO。
- `std::priority_queue`：優先度最大（比較設定による）の要素を取得。

A*探索のオープンリスト、イベントキュー、Undo履歴などに使えます。

## 所有と安定ID

コンテナの要素アドレスを外部へ長期保存すると、再確保や削除で壊れます。ゲームオブジェクトには次の選択肢があります。

- 容量を固定・予約し、規則を厳密に守る。
- `unique_ptr`をコンテナへ格納し、指される本体のアドレスを安定させる。
- インデックスと世代番号からなるハンドルを使う。
- 安定アドレスを保証する専用プールを使う。

どれも削除後の参照を自動的に解決するわけではないため、寿命契約が必要です。

## 選択時の質問

1. 要素数は固定か可変か。
2. 順序は必要か。
3. 主な操作は走査、検索、末尾追加、中央削除のどれか。
4. 要素への参照をどれだけ保持するか。
5. メモリ連続性とキャッシュ効率は重要か。
6. 決定的な反復順序が必要か。
7. 最大要素数と毎フレームの操作量はいくつか。
