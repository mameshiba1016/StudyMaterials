# エラー処理・例外・契約

エラー処理では、どの失敗が回復可能か、誰が判断するか、情報をどう伝えるかを設計します。すべてを例外、`bool`、ログだけで処理する方法はありません。

## エラーの分類例

- プログラマーのバグ：配列境界違反、不変条件違反、null禁止APIへのnull。
- 外部・実行時失敗：ファイル不在、通信切断、容量不足、無効なユーザーデータ。
- 通常の分岐：検索対象なし、入力なし、敵なし。必ずしも「エラー」ではない。
- 致命的失敗：必須アセット破損、初期化不能など、継続できない状態。

分類によって`assert`、戻り値、`optional`、`expected`、例外、終了の選択が変わります。

## `assert`

```cpp
#include <cassert>

void SetHealth(int hp)
{
    assert(hp >= 0 && "HP must not be negative");
}
```

開発時に「成立しているはずの前提」を検査します。`NDEBUG`で無効化され得るため、外部入力検証や必須処理を`assert`の副作用へ依存させません。リリースでも必要な検査には別の仕組みを使います。

## 戻り値

```cpp
bool TryLoadConfig(const std::filesystem::path& path, Config& output);
```

単純ですが、`false`の理由を表せず、出力引数がどの状態か契約が必要です。列挙エラー、結果構造体、`expected`などで情報を増やせます。

## `std::expected`（C++23）

```cpp
enum class LoadError
{
    NotFound,
    PermissionDenied,
    InvalidFormat
};

std::expected<Config, LoadError> LoadConfig(const std::filesystem::path& path);
```

成功時の値か失敗時のエラーを保持します。失敗がAPIの通常契約として予想され、呼び出し側へ明示したい場合に適します。利用する標準ライブラリのC++23対応状況は確認が必要です。

## 例外

```cpp
try
{
    LoadRequiredAsset();
}
catch (const std::filesystem::filesystem_error& error)
{
    std::cerr << error.what() << '\n';
}
```

例外は通常の戻り経路から離れて失敗を伝播し、途中スコープのRAIIオブジェクトを破棄します。投げられた型に合う`catch`へ到達しなければ`std::terminate`です。

### 例外使用時の原則

- 例外安全なRAIIを前提にする。
- デストラクタから例外を外へ出さない。
- 値で投げ、`const`参照で捕捉する。
- `catch (...)`で黙って握り潰さない。
- 例外を毎フレームの通常分岐へ使わない。
- プロジェクトやエンジンが例外を無効化しているか確認する。

Unreal Engineの一般的なゲームコードではC++例外に依存しない構成が用いられるため、戻り値、`ensure`、`check`、ログ等のエンジン規約を専用章で扱います。

## 例外安全保証

- no-throw保証：失敗しても例外を投げない。
- strong保証：失敗時に外部から見た状態が操作前と同じ。
- basic保証：不変条件を保ち、リソースリークしないが状態は変化し得る。
- 保証なし：失敗後の状態を保証しない。

すべての関数へstrong保証が必要なわけではありません。API契約として必要な水準を決めます。

## ログとユーザー表示

ログは原因調査の記録であり、エラー処理そのものではありません。内部パスや技術情報をユーザーへそのまま表示せず、ユーザー向けメッセージ、開発ログ、テレメトリを分けます。機密情報や個人情報をログへ残さない規則も必要です。

## フェイルセーフ

任意アセットが失敗したら代替テクスチャを使う、セーブ書込は一時ファイルへ行ってから置換するなど、破損や中断を前提に設計します。失敗を無視して不完全状態を進めることとは異なります。
