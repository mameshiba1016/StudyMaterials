# コード品質・命名・レビュー・リファクタリング

コード品質は見た目の統一だけではありません。正しさ、読みやすさ、変更容易性、テスト可能性、性能、診断可能性を、プロジェクトの目的に合わせて維持することです。

## 命名

名前は型と役割を伝えます。

```cpp
float elapsedSeconds{};       // 単位が分かる。
int remainingEnemyCount{};    // 何の個数か分かる。
bool isInvincible{};          // 真偽の意味が文として読める。
void ApplyDamage(int amount); // 動作と対象が分かる。
```

`data`、`temp`、`manager`のような広すぎる名前を多用しません。ループの短い`i`、数学の`x`など局所的に慣習が明確なら短名も適切です。

## コメント

コードの直訳より、理由、制約、単位、外部仕様、回避しているバグを記録します。古くなったコメントは誤情報なのでコードと同時に更新します。公開APIには前提、所有権、null可否、スレッド、無効化規則を文書化します。

## 一つの責任

「一関数は必ず10行以内」のような機械的基準ではなく、変更理由をまとめます。入力、物理、描画、保存を一関数へ混ぜるとテスト・再利用・並列化が難しくなります。

## DRYの誤解

見た目が似た二つのコードが、異なる理由で変化するなら無理に共通化しません。重複した知識・規則を一か所へ集めるのが目的です。早すぎる抽象化は大量のフラグ引数と条件分岐を生みます。

## SOLIDを目的化しない

SOLIDは設計を考える語彙ですが、インターフェースやクラス数を増やせば品質が上がるわけではありません。ゲームのホットパス、データ局所性、エンジン規約、小規模機能では異なる判断があります。変更予測と実測に基づきます。

## マジックナンバー

```cpp
constexpr float DodgeInvincibilitySeconds{0.18F};
```

意味ある名前、単位、調整元を与えます。ただし`0`、`1`の数学的に自明な利用まで全て定数化すると読みにくくなります。ゲーム調整値はデータ化し、範囲検証と既定値を持たせます。

## 関数引数

```cpp
SpawnEnemy(3, 5.0F, true, false); // 各値の意味が不明瞭。
```

設定構造体、enum、強い型、名前付きビルダーなどで意味を表します。

```cpp
EnemySpawnSettings settings{
    .count = 3,
    .intervalSeconds = 5.0F,
    .isElite = true
};
```

指示付き初期化子はC++20で、宣言順などの規則があります。

## コードフォーマット

clang-format等で機械的なスタイル議論を減らします。clang-tidy、警告、静的解析で危険パターンを検査します。ツール設定をリポジトリへ保存し、全員とCIで同じ結果にします。

## リファクタリング

外部動作を保ちながら内部構造を改善します。

1. 現在の動作をテスト・記録する。
2. 小さな変更を行う。
3. ビルド・テスト・計測する。
4. 一つの目的でコミットする。

機能変更と大規模整理を同時に行うと、レビューと原因追跡が難しくなります。

## コードレビュー

確認項目の例：

- 仕様と境界値を満たすか。
- 所有権と寿命が明確か。
- エラー経路とログがあるか。
- スレッド規則を守るか。
- テストは失敗を検出できるか。
- 性能上重要なら計測があるか。
- セキュリティ、入力検証、権限に問題がないか。
- API名とコメントが契約を正しく表すか。

人格ではなくコードとリスクを扱い、指摘には理由と再現例を付けます。

## 最適化

まず正しい設計と計測可能性を作り、プロファイラで支配的コストを特定します。ただし、アルゴリズムとデータ配置の大きな選択は後から変えにくいため、要件上の規模を早期に把握します。「早すぎる最適化を避ける」は性能を考えないという意味ではありません。

## 完成の定義

コードを書き終えただけでなく、ビルド、テスト、警告、ドキュメント、エラー処理、性能予算、配布手順、ライセンスを満たして完成です。学習用プロジェクトでも、自分が担当した範囲と判断理由を説明できることは品質理解の一部です。
